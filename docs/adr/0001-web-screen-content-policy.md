# Web 화면의 서드파티 콘텐츠는 가짜 영상 임베드 하나뿐이고, HTML은 렌더링하지 않는다

Bridge가 Message의 출처를 반드시 검증해야 하는지는 Web 화면 안에서 무엇이 실행되느냐에 달려 있다. Reference App은 서드파티 콘텐츠를 프레임으로만 들이고, 그 예로 Web과 다른 출처에서 띄우는 가짜 영상 플레이어를 아티스트 글 하나에 임베드한다. 메인 프레임에서는 우리 번들만 실행되고, 글은 쓴 사람과 상관없이 일반 텍스트에 자동 링크만 붙여 렌더링한다. 실제 팬덤 앱에는 영상 임베드가 거의 늘 있으므로, 이 구조를 가져다 쓴 앱이 임베드를 붙여도 Bridge가 열리지 않도록 출처·프레임 검증을 Reference App에서부터 실제로 동작시킨다.

## Considered Options

- **iframe을 두지 않는다**: 출처 검증이 필요 없어 가장 단순하다. 하지만 가져다 쓴 앱이 임베드를 붙이는 순간 Bridge가 열리고, Android에서는 Host 내비게이션 콜백으로 iframe을 막을 수 없다.
- **실제 영상 서비스를 임베드한다**: 테스트가 네트워크·약관·재생 조건에 묶인다.
- **운영자 글은 허용 태그만 남긴 HTML로 렌더링한다**: 아티스트·운영자 화면은 범위 밖이고, 시나리오에 서식이 필요 없다.

## Consequences

- 출처·프레임 정보를 주지 못하는 WebView 구성과 "콘텐츠 통제만" 하는 보안 모델은 쓸 수 없다.
- 메인 프레임에서 실행되는 스크립트는 출처 검증으로 걸러지지 않는다. 분석·에러 수집 SDK 같은 서드파티 스크립트를 붙이면 Bridge 전체 권한을 준 것과 같다.
- 콘텐츠 속 링크는 딥링크와 같은 경로 표로 판정한다. 경로 표 밖의 Web 출처 주소(업로드 파일 등)는 메인 프레임에서 열리지 않는다.
- 임베드 안에서 이동하면 그 기록이 WebView의 기록에 섞여, 뒤로가기가 메인 프레임 대신 임베드를 되돌린다. 가짜 영상 플레이어는 페이지 하나로 만들어 안에서 이동하지 않게 하고, 실제 임베드를 붙이면 이 위험이 생긴다([ADR 0008](0008-web-owns-back-in-tab-webview.md)).
